### 1.2 ⚠️ 官方规范 vs 我们仓库的一条冲突（这条我要认错）

**官方原文**（`h3res/guide_base_en.md` §4.4，我核对过）：

```text
The young woman with a quiet, breathy voice (S1) says: <d>[English] I get off at the next station.</d>
```

`<d>` **就是官方规定的台词写法**：`<d>` 外写说话人身份/编号/语气，`<d>` 内只放**语言标签 + 逐字原文**（不翻译、不改标点）。

**我们仓库的规矩却在说不要用它** —— 而且这个错是**我在 `docs/仓库规矩与skill总览.md` 里写下的**：

| 文件 | 原文 | 问题 |
| --- | --- | --- |
| `START_HERE_MANUAL_COMFYUI.md` 第 5 条 | "**提示词里写 `<d>[Chinese] …</d>` 会被模型画成画面字幕**。…加 `No subtitles, captions or on-screen text appear at any point.` 即可消除。" | ✅ 原始记录正确：**现象 + 补救办法** |
| `docs/MiniMax_H3_使用与避坑手册.md` 第 4 坑 | "画面里烧进字幕 ← 提示词里的 `<d>` 被当成画面文字 ← **加 `No subtitles…` 那句**" | ✅ 同样正确：补救办法是**加那句话** |
| **`docs/仓库规矩与skill总览.md`（我写的）** | "**不写 `<d>[Chinese]`**，改用官方句 `No subtitles…`" | ❌ **写错了**：把"加这句话来补救"曲解成"别用 `<d>`，换成这句话" |

**正确口径应该是**：**台词照官方用 `<d>[语言] 原文</d>` 写，同时在提示词里加 `No subtitles, captions or on-screen text appear at any point.` 来压掉烧字幕。** 不是二选一。

> 这一条本身就是"混乱"的活标本：**原始记录是对的，索引文档转述时把它转坏了**，而索引文档正是新 AI 最先读的东西。这直接印证了 §5 的判断 —— 问题不在规矩数量，在**没有单一权威 + 没有检查**。

### 1.4 H3 的实测行为规律（能直接改我们的分镜规则）【我核实过 README 原文】

**[phileiny/h3-storyboard-skill](https://github.com/phileiny/h3-storyboard-skill)** ★165 · 2026-08-28 · MIT。
作者用**同 seed / 同参考 / 逐步只改一个变量**的对照实验得出（README 里有完整 PSNR 表）：

| 现象 | 数据 | 对我们的意义 |
| --- | --- | --- |
| **一个镜头塞太多面部指令 → H3 静默丢弃** | 7 秒特写塞 9 个 beat → 峰值 PSNR **37–42 dB（=画面冻结）**；拆成 3 个 2–3 秒单 beat 镜头 → **22–23 dB，每个 beat 都生效** | **分镜粒度硬规则**：一个镜头最多 2–3 个表情 beat |
| **`<d>` 不会让脸动，而是抢屏幕时间** | 情绪镜头 55 帧 → 84 帧（提示词只要 74）；**下一镜 56 → 42 帧**，背景角色消失、玻璃门退化成普通窗 | 给某镜加台词会**牺牲相邻镜头**，排段落时要留余量 |
| **尾部塌陷** | 每段结尾前 **1.2–1.7 秒**画质劣化 | segment 时长预算必须留尾 |
| 沉默角色没有口型挂点 | —— | 改用身体表演；"最后一公里是剪辑不是提示词" |

作者还专门写了一节**更正自己早期的错误归因**（早期以为 `<d>` 是脸不动的原因，后来补做对照组发现是"一次改了两个变量"）。**这种"区分有对照实验 vs 仍属推断"的写法，正是我们 `02_工作规则.md` 要求的"给数字不给形容词"** —— 值得直接学它的 `SOURCES.md` 体例。

### 1.5 「分镜图 = 视频首帧」的成本论证【子代理核实】

**[A-cat-with-carrots/OnlyShot](https://github.com/A-cat-with-carrots/OnlyShot)** ★282 · 2026-07-07 · MIT。
主张：image2video 占 80%，所以**先把分镜图当首帧做死，再出视频**。成本对比：**分镜图 3 积分/张 vs 视频 55 积分/段 ≈ 1/18**。
含 24 集 / 36 grid × 4–10 秒的节奏地图、80–150 张工业 ref 库规格、**17 条失败模式**。

> 这正好给我们「先出首帧再出视频」的做法提供了**量化依据** —— 之前只是经验，现在有数字。

## 4. 生态的两个空白（= 我们的原创机会）

本次核实了 **≥12 个真 SKILL.md 短剧包**，但有两个系统性空白：

### 空白一：横屏（16:9）
绝大多数默认 **9:16 竖屏**。真正处理横屏的只有：
- `suihe1/short-drama-production`（**默认就是 16:9**）
- `xixihhhh/ai-short-drama-skill`（Dramake，横竖屏显式设计，`Identity & Style Lock` + `Model Router` 含 MiniMax H3）

我们**从竖屏改横屏**踩的坑（`sensor_fit=VERTICAL`、1344×768 是 7:4 不是 16:9、焦距反推表），**在这个生态里几乎没有现成答案** —— 这部分我们的文档是有价值的。

### 空白二：本地 ComfyUI + Qwen-Image 的角色一致性
**没有任何中文 skill 覆盖这条链。**
- `h3lite` 管 H3 生成，`ComfyUI_Qwen_H3_Prompt` 管提示词生成
- 但「**Qwen-Image 出锚图 → Edit-2511 派生视图 → 一致性锁定 → 喂给 H3**」这条链**要我们自己写**

> 这可能是我们项目**最值得沉淀成原创 skill** 的部分。我们已经在做（锚图派生链、本地裁切细节件、angles LoRA 换机位），只是还没把它写成可复用的 skill。

**但它们给的理由是成本与工作流，不是"Qwen-Image 画得差"**：
- **按张计费极便宜**：`research/C_quantitative_data.md` 记「一部 100 集漫剧约需 800–1500 张图…按 API 计费约 0.02–0.1 元/张，**画面总成本 20–150 元**」；`research/_mynotes-pipelines.md` 记 GPT-Image-2 低至 $0.006/张。

**所以准确的结论是**：**"agent skill 生态"和"本地 ComfyUI/Qwen-Image 生态"几乎不重叠** —— 前者假设云 API、把出图抽象成 `$imagegen`（`shuohao-skills` 原文就是「分镜图出图走 codex `$imagegen`」）；后者没有 skill 层。我们正好卡在交叉地带：**既是 agent 驱动（要 skill），又是本地 ComfyUI + Qwen-Image（没现成 skill）**。

空白是真的，但它是"**交叉地带没人做**"，不是"**工业界否定了这条路**"。

> **对我们的实际含义**：工业界的做法不等于我们该照抄（我们图的是零按张成本、数据不出本机、可训 LoRA、中文文字强）。但有一条**值得你拍板**：我们反复卡在**角色脸不像 + 人体比例**，而工业解法（参考图 + 主体一致性）在云模型上是开箱即用的。**是否引一条云通道做对照/混合**（关键角色卡走云、量产帧走本地）——这是性价比问题，不是对错问题。

#### ✅ 结论（**用户实测后拍板，2026-09-20**）——**不引云通道**

用户用已有的 ChatGPT Plus ＋ 即梦/Seedream 手工出图与本地 Qwen-Image 对照，**目视判断（按 `agent.md` §一.4，感知类结论由人判断，此为权威口径）**：

> **「没有太多明显的差距。主要差距可能就是风格切换，它们比较灵活，我们需要摸索，就这点差别。其他的大差不差。」**

**因此**：
- **不引入云图像通道**（Phase 1 不需要）。理由不是钱，是**质量差距不足以换来一次返工**。
- 本地路线的 11× 单价优势（见 `pipeline/docs/05_成本与产能.md`）**保留**。
- **唯一被确认的真实差距是「风格切换灵活度」** → 这是下一步该补的技术项，见下。

#### 🎯 由这条结论导出的唯一待办：把「风格摸索」变成「查表 / 给图」

我们**已经知道机制**（`HANDOVER_2026-09-19_模型升级与风格锁定.md` §5.2"本轮最值钱的一条"）：

| 写法 | 结果 |
| --- | --- |
| `3D渲染` / `动漫插画` / `游戏CG`（泛类别词） | ❌ 拉不动 2512，仍出真人照 |
| `皮克斯（Pixar）三维动画电影风格` | ✅ 真·三维动画角色 |
| `日本二维动画（anime）赛璐璐上色风格` | ✅ 真·二维赛璐璐动漫 |

**泛类别词无效、具名风格有效** —— 所以"要摸索"的本质是：**我们得为每个想要的画风找到那句正确的具名短语**，而这目前靠试。

**三条可选补法（按省事程度排）**：

| # | 做法 | 依据 / 为什么可行 | 成本 |
| --- | --- | --- | --- |
| **①** | **用风格参考图，而不是用词**：把一张目标画风的图接进 Edit-2511，提示词只写「画风与 Image 1 完全一致」 | 我们已实测**Edit 继承输入图**极强（纯提示词与 exclude 都改不动构图，§`01_资产规范.md` §6.1）。既然连构图都继承，**画风更会继承** —— 只是我们还没把它用在"风格"上 | 最低，复用现有链路 |
| **②** | **建一张「具名风格词表」**：把 `.work/nc_photoreal_test.py`（PH1–PH23 实验台）扩成正式台账 —— 每个风格的**提示词原文 + 出图样例 + 命中/未命中** | 把"摸索"变成"查表"；`shuohao-skills` 也有 `references/style-presets.md` 可参考 | 低，纯实验 + 文档 |
| **③** | **训一个画风 LoRA**（一个风格 = 一个词） | [FlyMyAI/flymyai-lora-trainer](https://github.com/FlyMyAI/flymyai-lora-trainer) ★766 是 Qwen-Image 的 LoRA 训练器 | 最高，**32GB 能否训 20B 模型未评估** |

> **建议先做 ①**：它不需要新模型、不需要训练，只是把已经验证过的「Edit 继承输入图」这条规律换个用途。如果 ① 够用，②③ 都可以不做。

### 顺带：Qwen-Image 侧的两个发现

## 5. 🔧 「目前来看很混乱，极易造成 AI 乱用」—— 根治方案

### 5.1 混乱的真实成因（我的判断）

不是"规矩太多"，是这三条：

| 症状 | 具体表现 | 后果 |
| --- | --- | --- |
| **一个事实写在多处** | 同一条 H3 规则在 `PROMPT_给新AI.md` / `h3-mapping.md` / `MiniMax_H3_使用与避坑手册.md` / 交接里各写一遍，措辞不同 | AI 读到哪条算哪条 |
| **没有优先级仲裁** | 14 处矛盾（见 `docs/仓库规矩与skill总览.md` §4）全靠人记 | 新 AI 必踩 |
| **规矩不可检查** | 60 条规矩**没有一条**是脚本能验的 | AI 可以"遵守了"却实际违反，且没人发现 |

### 5.2 别人的解法（我们直接抄）

| 仓库 | 机制 |
| --- | --- |
| `zenstory-ai/drama-skills` | **每集只维护 5 份 md 作为唯一事实**（剧本/视觉设定/分镜/图片提示词/视频提示词）；**检查脚本核对"这一镜声明依据了哪些条目"**，漏了直接报错 |
| `eternityspring/shuohao-skills` | **14 / 11 / 10 / 17 道质量门，全部脚本检查**，不是写在文档里让人自觉 |
| `suihe1/short-drama-production` | `production.json` 记**制品哈希 + 依赖**；上游改了角色 → 下游**自动标 `stale` 并要求重新审批**；导演意图与技术执行分层 |
| `phileiny/h3-storyboard-skill` | `SOURCES.md` **显式区分**"有对照实验支撑"vs"仍属推断" |

**共同点：规矩不是文档，是可执行的检查。**

### 5.3 我建议的改法（**待你批准，不擅自改**）

**第一步：立一份唯一的「硬规矩」文件（≤15 条）**
放在根目录，AI 每轮必读。只保留**违反会造成真实损失**的：凭据、删文件、并发显存、探测下载、汇报格式、感知判断交给人。
其余全部降级为"参考/历史"，在文件头加 `> ⚠️ 历史文档，规则以 <根目录硬规矩> 为准`。

**第二步：把能查的规矩变成 `check.py` 门禁**
优先做这 4 个（都是我们已经反复踩的）：
1. 分镜表三列自洽（`lens_mm/dist_m/visible_w_m` 与景别匹配）
2. H3 帧数落在 `17k+5`
3. H3 每镜表情 beat ≤ 3、每段留 1.7 秒尾部余量（**来自 §1.3 的实测**）
4. 资产引用完整性（分镜里出现的 CHR/SCN/PRP 编号必须在资产表里存在且已锁版本）

**第三步：一份「事实台账」取代分散的进度记录**
类似 `production.json`：记每个产物的**哈希 + 依赖 + 审批状态**。上游改一张角色卡 → 下游首帧自动标脏。

**第四步：认领上游 skill，不再重复造**
- 拉官方 `h3-prompt-writing`（`base-en.txt` / `ref-en.txt`）作为 H3 规范的**唯一来源**
- 我们的 `h3-mapping.md` 改成"官方规范的本地补充（横屏 + 本地 ComfyUI 路径）"
- `.zcode/skills/3d-animation-short-generator/` 标注为"官方 H3 套件成员，非外部不可用 skill"
- 做一次与上游的 diff
